\section{Experiments}
\label{sec:experiments}

We evaluate SceneFactory along three axes:
simulation throughput (\S\ref{sec:throughput}),
end-to-end navigation performance on held-out Waymo scenes (\S\ref{sec:navigation_perf}),
and qualitative trajectory analysis (\S\ref{sec:qualitative}).
All experiments use a single shared navigation policy trained with PPO; the contribution of this work is the simulation platform itself, so we report policy performance as an end-to-end validation of the pipeline rather than as a claim of state-of-the-art driving.

% ---------------------------------------------------------------
\subsection{Experimental Setup}
\label{sec:exp_setup}
% ---------------------------------------------------------------

\paragraph{Hardware and software.}
All training and evaluation runs execute on a single NVIDIA RTX PRO 6000 Blackwell GPU (96\,GB VRAM).
The software stack consists of
NVIDIA Isaac Sim Full 5.1.0,
Isaac Lab 0.54.3 ~\cite{nvidia_isaac_2025},
RSL-RL 3.1.2 for PPO,
PyTorch 2.7.0+cu128, and
CUDA 12.8.
Physics runs at 120\,Hz (time step $\Delta t = 1/120$\,s);
the control policy acts at 30\,Hz (decimation factor 4).

\paragraph{Scene curation.}
From approximately 1{,}000 Waymo Open Motion Dataset scenarios~\cite{Kan_2024_icra},
we extract candidate road topologies through the pipeline described in \S\ref{sec:data_processing}.
A human operator first visually inspects each candidate scene with a curation wizard that renders lane-center polylines, road-edge polylines, and origin-destination pairs.
The operator accepts scenes that have plausible road geometry and rejects those with degenerate lane structure, multi-level overlaps from z-flattening, or unreachable goals (see \S\ref{sec:sharp_edges} for rejection criteria).
This produces \textbf{64 training scenes} and a disjoint set of \textbf{64 held-out test scenes}.
Within each accepted scene, an automated filter then retains only those agents whose start and goal positions both lie within the 400\,m $\times$ 400\,m world bounding box, are separated by at least 3.0\,m, and have valid coordinates.
Up to 16 qualifying agents are extracted per scene; scenes with fewer valid agents leave the remaining agent slots inactive.

\paragraph{Training configuration.}
Each training scene is replicated four times to fill $64 \times 4 = 256$ parallel environments, each hosting up to 16 agent slots, for a nominal capacity of 4{,}096 agents.
In practice, many Waymo scenes contain fewer than 16 qualifying agents after the spawn filter described below, so slots without a valid spawn remain inactive throughout the episode.
Worlds are assigned to environments by random shuffling (seed~42), so every PPO update samples transitions from all 64 unique road topologies.
Episodes last 50\,s (1{,}500 control steps).
Upon reaching the goal (within 3.0\,m) or triggering a termination condition (collision, off-road crash, timeout), an agent is parked in place with zero velocity; the remaining agents continue until every agent in the environment has terminated or the episode times out, at which point the entire world resets with fresh start-goal assignments for all agents.

\paragraph{PPO hyperparameters.}
Training uses PPO with an adaptive learning rate (initial $2.09{\times}10^{-4}$, KL target 0.01), rollout horizon of 128 steps, 5 gradient epochs over 16 mini-batches, $\gamma{=}0.99$, $\lambda{=}0.98$, and clip $\epsilon{=}0.15$.
The total batch size per update is $4{,}096 \times 128 = 524{,}288$ transitions.
The full hyperparameter table is in Appendix~\ref{app:ppo_hparams}.

\paragraph{Evaluation protocol.}
We evaluate on the 64 held-out test scenes, each loaded into a separate environment with up to 16 agent slots.
Across the 64 test worlds, 624 of the 1{,}024 nominal slots contain a valid spawn (the remainder correspond to scenes with fewer than 16 qualifying agents).
The policy runs in deterministic mode (mean of the action distribution).
Evaluation uses \emph{invincible mode}: collisions and off-road events are logged but do not terminate the agent, allowing it to continue toward the goal so that we can measure the unconditional goal-reach rate.
An agent is counted as successful if it reaches within 3.0\,m of its assigned goal before the 50\,s episode deadline.

\subsection{Throughput}
\label{sec:throughput}
% ---------------------------------------------------------------

A core engineering contribution of SceneFactory is throughput: training with full rigid-body dynamics at a rate that makes large-scale PPO practical on a single GPU.
To quantify this, we compare SceneFactory against its direct predecessor, a pipeline built on the same Isaac Sim simulator and PhysX 5 solver but using the built-in Vehicle Wizard vehicle model and Stable-Baselines3 for PPO (hereafter ``Baseline'').
Both pipelines load the same Waymo scene, use 16 agents per world, identical observation features (350 road points, 24 vehicle neighbors with TTC), and run on the same RTX PRO 6000 Blackwell GPU.
The only differences are the vehicle representation, the environment wrapper architecture, and the RL framework.

\paragraph{Metric.}
We report \emph{controlled agent steps per second} (CASPS): the number of policy-controlled agents that complete one 30\,Hz control tick per wall-clock second.
Both pipelines log CASPS every PPO iteration via embedded sub-phase timers;
we discard the first 50 logged iterations as warmup and report the mean and standard deviation over the remaining steady-state samples.

\paragraph{Scaling experiment.}
We select a single Waymo scene with 28 qualifying agents (ensuring all 16 slots are filled in every world) and replicate it at four scales: 32, 64, 128, and 256 parallel worlds, yielding 512 to 4{,}096 agent slots.
Each configuration trains for a short benchmark window: 500\,K total timesteps for the Baseline, 20 PPO iterations for SceneFactory.
Figure~\ref{fig:throughput_scaling} plots CASPS as a function of total agent slots for both pipelines.
The Baseline throughput is essentially flat at $\sim$152--174 CASPS across all world counts, confirming that per-agent Python loops---not the PhysX solver---are the bottleneck.
SceneFactory scales near-linearly, reaching 19{,}250 CASPS at 256 worlds (4{,}096 agent slots): a \textbf{127$\times$ speedup} over the Baseline at the same scale.
Even at the smallest configuration (32 worlds), SceneFactory is 22$\times$ faster.
Neither pipeline exceeded GPU memory at 256 worlds on the RTX PRO 6000 Blackwell (96\,GB VRAM).

\paragraph{Why the speedup.}
The speedup arises from three architectural changes: (1)~GPU-resident joint-state tensors that replace per-agent Python loops with batched \texttt{torch} operations, (2)~cloned PhysX solver islands that enable parallel broad-phase/narrow-phase dispatch, and (3)~an on-device training loop (RSL-RL) that eliminates CPU--GPU data transfers.
A detailed per-phase timing breakdown (physics, observations, rewards, actions) is provided in Appendix~\ref{app:throughput}.

\paragraph{Comparison with kinematic simulators.}
Table~\ref{tab:cross_simulator} places SceneFactory in the context of published throughput numbers from kinematic driving simulators.
GPUDrive~\cite{kazemkhani_gpudrive_2025} (ICLR 2025) reports a peak of 2.3\,M agent-steps per second (ASPS) on an A100 GPU using a kinematic bicycle model.
When restricted to \emph{controlled} agents---i.e., those with non-trivial goals---the effective rate drops to $\sim$200\,K CASPS due to the high fraction of parked or near-goal vehicles in randomly sampled Waymo scenes (mean $\sim$10.8 controllable agents per scene out of up to 128 agent slots).
During end-to-end PPO training the authors report 200\,K--500\,K CASPS depending on hardware and observation configuration.
Nocturne~\cite{vinitsky_nocturne_2022} (NeurIPS 2022), a CPU-based C++ simulator with a kinematic model, achieves $\sim$15\,K ASPS on 16 CPU cores.
Waymax~\cite{gulino_waymax_2023} (NeurIPS 2024), a JAX-based simulator, supports full GPU vectorisation via \texttt{jax.vmap}/\texttt{jit}. We benchmarked Waymax on the same RTX PRO 6000 at 64 parallel scenes $\times$ 16 agent slots---matching SceneFactory's world count---using \texttt{DeltaGlobal} kinematic dynamics, a scripted constant-speed actor, and a 350-point per-agent road-geometry observation. Scenarios were drawn from a real WOMD training shard (455 unique scenes), cycling through four distinct preloaded batches to avoid cache artifacts. Under this configuration Waymax achieves $\sim$64\,M CASPS$^\dagger$. The $\sim$3{,}300$\times$ gap relative to SceneFactory reflects the difference in per-step cost: Waymax's kinematic step is a single trigonometric integration, whereas SceneFactory runs a 10-DOF PhysX articulated-body solver at 120\,Hz plus a PPO policy forward pass.

SceneFactory operates at a lower absolute throughput than GPUDrive because each agent is a 10-DOF articulated rigid body simulated by the PhysX 5 solver at 120\,Hz (four physics sub-steps per 30\,Hz control tick).
The comparison is not apples-to-apples: the physics fidelity that makes SceneFactory useful for sim-to-real transfer---tire slip, suspension dynamics, inertial coupling---is precisely what makes it slower than a kinematic model.
Nevertheless, at 19.3\,K CASPS SceneFactory already exceeds Nocturne's throughput while providing full rigid-body dynamics, and it operates within an order of magnitude of GPUDrive's training-time CASPS despite the fundamentally heavier physics workload.
The relevant same-hardware, same-physics comparison is against the Baseline pipeline on the same RTX PRO 6000, where SceneFactory achieves a \textbf{127$\times$} speedup (Table~\ref{tab:throughput_scaling}).

\paragraph{Comparison with MetaDrive (physics-based, measured on our hardware).}
To complement the published kinematic-simulator numbers, we directly measure the throughput of MetaDrive~\cite{li2022metadrive} on the same RTX~PRO~6000 machine.
MetaDrive uses the Bullet rigid-body physics engine and, like our non-vectorized Baseline, issues actuation, observation, and reward computations through per-agent Python loops.
We run \texttt{MultiAgentRoundaboutEnv} at agent counts of 1, 4, 8, 16, 32, and 40 (the spawn-geometry ceiling for this map), using random actions to isolate loop overhead.
CASSPS is measured over 10 steady-state windows of 500 steps each after a 200-step warmup, mirroring the Baseline protocol.
MetaDrive peaks at $\sim$1{,}390 CASPS with 8 agents and \emph{declines} to 1{,}050 CASPS at 40 agents---confirming that per-agent Python loops, not the physics solver, are the throughput bottleneck, independently of whether the backend is PhysX~5 or Bullet.
Critically, MetaDrive has no multi-world parallelism axis: each process simulates exactly one scene at a time.
SceneFactory exposes a \texttt{num\_worlds} scaling dimension that MetaDrive's architecture does not support; at the smallest SceneFactory configuration (32 worlds, 512 agent slots) SceneFactory already achieves 3{,}870 CASPS---a \textbf{2.8$\times$} advantage over MetaDrive's per-scene peak, growing to \textbf{13.9$\times$} at 256 worlds (4{,}096 agent slots).

\subsection{Navigation Performance}
\label{sec:navigation_perf}
% ---------------------------------------------------------------

We train a single shared navigation policy across all 4{,}096 agent slots (256 worlds $\times$ 16 agents) using PPO and select the best checkpoint by validation goal-reach rate.
The selected checkpoint (model\_975) corresponds to approximately $975 \times 128 \times 4{,}096 \approx 511\text{M}$ environment steps.

\paragraph{Evaluation protocol.}
All evaluations use \emph{invincible mode}: collision, lane-boundary, and off-road events are logged but do not terminate the agent, so that every spawned vehicle is observed until it either reaches its goal (within 3.0\,m) or the 50\,s episode budget expires.
This protocol allows us to measure goal-reach rates without survivorship bias.

\paragraph{Generalization study.}
To assess how well the learned policy generalizes across scenes and routing targets, we evaluate the same checkpoint under three conditions that progressively decouple the test setting from the training distribution:
%
\begin{enumerate}[leftmargin=*, itemsep=1pt]
  \item \textbf{Test scenes, original OD.}
        64 held-out Waymo scenes with the original origin--destination pairs extracted from the dataset.
  \item \textbf{Test scenes, random OD.}
        The same 64 held-out scenes, but each agent's destination is re-sampled uniformly along reachable road segments at 10--100\,m travel distance.
  \item \textbf{Train scenes, random OD.}
        The 64 unique training scenes, each with 16 randomly sampled origin--destination pairs (10--100\,m travel distance), for a total of 1{,}024 agents---matching the test-scene agent count.
\end{enumerate}

\paragraph{Random OD protocol.}
We adopt a 10--100\,m travel-distance range for the random OD protocol.
This range is deliberately wide: short routes (10--20\,m) test low-speed goal approach and braking precision, while long routes (60--100\,m) require sustained lane-following, multi-turn navigation, and interaction with neighboring vehicles.
The upper bound of 100\,m is constrained by the 400\,m $\times$ 400\,m world bounding box---routes longer than $\sim$100\,m frequently violate the ``goal within bounds'' filter and produce too few valid OD pairs.
We verified that the 10--100\,m range yields 1{,}024 valid spawns (all 16 slots filled) in every evaluation scene, avoiding sparse-agent artifacts that would arise with longer routes.
Compared to a narrower 20--60\,m band, the wider range is a more demanding test of route generalization and better represents the diversity of real-world driving distances.

On held-out test scenes with original destinations, the policy reaches its goal in 71.6\% of cases (447 of 624 agents) with a mean residual distance of 10.1\,m for non-successful agents.
When the same test scenes are paired with randomly sampled destinations at 10--100\,m travel distance (Condition~2), the success rate rises to 84.5\% (865 of 1{,}024 agents), matching \emph{exactly} the 84.5\% achieved on training scenes with the same random-OD protocol (Condition~3).
The identical performance between Conditions~2 and~3 is the central finding: \emph{the policy generalizes to entirely novel road geometries as well as it performs on familiar ones}, when the routing difficulty is controlled.
This rules out scene memorization and confirms that the policy has learned a general goal-conditioned navigation strategy.

The 13-percentage-point gap between Conditions~1 and~2 (71.6\% vs.\ 84.5\%), which share the same test scenes but differ only in OD pairs, reveals that the original Waymo destinations are substantially harder than the 10--100\,m random-OD protocol.
The Waymo-extracted routes include long-range multi-turn trajectories, goals near road boundaries, and occasionally ambiguous lane assignments that the random sampler avoids by construction.
We also verified this trend at a narrower 20--60\,m travel range, where the success rate reaches 92.8\% on the same test scenes---confirming that shorter, simpler routes inflate the headline number without meaningfully testing navigation capability.
This motivates our choice of the wider 10--100\,m band, which provides a more demanding and representative evaluation.
Further gains on the original OD setting are achievable through longer episodes, curriculum over route difficulty, or improved goal-approach behavior, rather than additional scene diversity.

The collision rates remain low across all conditions (3.6--6.3\%), and are inflated by invincible mode, which allows post-collision agents to continue driving and potentially trigger additional collision events; under normal termination semantics each collision would end the episode immediately.
Notably, the off-road crash rate is higher on test scenes (16.9\%) than on training scenes (15.9\%) under the same 10--100\,m random-OD protocol, indicating that novel road geometries do cause slightly more lane departures---but the policy recovers and still reaches the goal at the same rate.

\paragraph{Comparison with kinematic simulators.}
GPUDrive reports near-perfect goal-reach rates ($>$98\%) on Waymo scenes using a kinematic bicycle model with no rigid-body dynamics.
We attribute the gap primarily to the harder control problem posed by full PhysX dynamics: the policy must learn to manage tire slip, suspension oscillations, and inertial overshoot that do not exist in kinematic models.
The 10-DOF articulated vehicle with effort-based actuation (\S\ref{sec:action_space}) requires the agent to implicitly discover braking distances, cornering limits, and steering lag, whereas a kinematic model executes velocity commands with no delay or slip.
Closing this gap through longer training, refined reward shaping, and curriculum design is active work; the current results demonstrate that the platform successfully trains navigating agents end-to-end under physically realistic dynamics.

\subsection{Ablation: Does Scene Curation Matter?}
\label{sec:ablation_curation}
% ---------------------------------------------------------------

The evaluation protocol in \S\ref{sec:navigation_perf} relies on a human-curated set of 256 training scenes.
A natural question is whether this manual curation step is necessary for training a performant policy, or whether simply sampling scenes at random from the valid pool would suffice.
If curation is unnecessary, the entire pipeline becomes fully automated and can scale to arbitrary dataset sizes without human bottleneck.

\paragraph{Experimental setup.}
We train a second policy (\textbf{Random-256}) using the identical PPO configuration, reward function (v6-patient), and network architecture as the curated baseline (\textbf{Curated-256}), changing only the scene selection:
instead of the 256 hand-curated scenes, we uniformly sample 256 scenes at random (seed~2024) from the 449 valid Waymo scenarios that pass the automated geometric filters (bounding box, minimum road segments, reachable goals) but \emph{without} any human visual inspection.
This random pool therefore includes scenes that the human curator would have rejected.

Both models train for 1{,}200 PPO iterations on a single RTX PRO 6000 Blackwell GPU.
For comparison we select \texttt{model\_975} from the curated run ($\sim$511M environment steps) and \texttt{model\_1100} from the random run ($\sim$577M environment steps).

We evaluate both checkpoints under three conditions that vary both the scene set and the origin--destination (OD) protocol:
%
\begin{enumerate}[leftmargin=*, itemsep=1pt]
  \item \textbf{Unseen scenes, original OD.}
        64 held-out test scenes with dataset-extracted OD pairs (624 valid agents out of 1{,}024 nominal slots).
        This is the hardest condition: novel road geometry and long-range Waymo-extracted routes.
  \item \textbf{Seen/training scenes, random OD.}
        64 of each model's own training scenes (subsampled via \texttt{random\_envs} mode), with randomly re-sampled OD pairs at 10--100\,m travel distance along reachable road segments (1{,}024 agents).
        This condition tests in-distribution road geometry with novel routing under the same random OD protocol as Condition~3.
  \item \textbf{Unseen scenes, random OD.}
        The same 64 held-out test scenes, but with randomly re-sampled OD pairs at 10--100\,m travel distance (1{,}024 agents).
        This condition tests both novel geometry and novel routing.
\end{enumerate}
%
All evaluations use invincible mode (events logged but agents not terminated) with a 50\,s episode budget, deterministic policy rollout, and 3.0\,m goal threshold.

\paragraph{Results.}
Table~\ref{tab:curation_ablation} reports per-agent success rate (SR), collision rate (CR), and lane-forbidden rate (LF) across all six conditions.

\paragraph{Discussion.}
The central finding is that \textbf{scene curation has negligible impact on policy performance}.
Across all three evaluation conditions, the agent-level success rate delta between Curated-256 and Random-256 is at most 1.2 percentage points, and in the hardest condition (unseen scenes with original OD pairs) the two models achieve \emph{identical} success rates of 71.6\%.

On seen/training scenes with random OD (Condition~2), the two models are virtually indistinguishable: $\Delta\text{SR} = {+}0.5\%$ ($85.0\%$ vs.\ $84.5\%$).
Using the same 10--100\,m random OD protocol for both training-scene and unseen-scene evaluation (Conditions~2 and~3) yields directly comparable numbers and confirms that the difficulty is dominated by the long-route component rather than scene geometry.

On unseen scenes with random OD (Condition~3), the curated model holds a modest +1.2\% SR advantage---the only condition where curation helps---but this difference is well within the range of inter-checkpoint variation and is unlikely to be statistically significant given the 64-world sample size.

The collision rate is consistently $\sim$2--3\% higher for the random model across all conditions, while the lane-forbidden rate is consistently $\sim$1--1.5\% lower.
These small, systematic offsets may reflect differences in the road geometry distribution (random scenes include more unusual lane structures that are harder to navigate but also have simpler lane boundaries), but neither effect is large enough to affect the overall viability of the policy.

\paragraph{Implications.}
This result has significant practical implications for the SceneFactory pipeline.
The human curation step---which requires a domain expert to visually inspect each candidate scene---was originally considered essential for filtering out degenerate road geometries that could corrupt training.
The ablation demonstrates that the automated geometric filters alone (bounding-box check, minimum road-segment count, reachable goal verification) are sufficient to produce a training-quality scene set.
This means the pipeline is \textbf{fully automated end-to-end}: given a collection of Waymo TFRecords, SceneFactory can generate training environments, train a multi-agent navigation policy, and evaluate on held-out scenes without any human intervention.
This is critical for scalability---the approach can ingest thousands of scenes without a curation bottleneck.

\subsection{Ablation: Does Friction Awareness Matter?}
\label{sec:ablation_friction}
% ---------------------------------------------------------------

SceneFactory exposes a physics-based weather-to-friction module (\S\ref{sec:weather_friction}) that computes per-world tire--pavement friction coefficients and encodes them into the policy observation.
A natural question is whether this friction-aware training is actually necessary: does a policy trained without any friction variation---assuming dry asphalt throughout---suffer a meaningful performance drop when deployed on wet roads?
To answer this, we compare two policies that differ \emph{only} in their friction training regime:

\begin{itemize}[leftmargin=*, itemsep=2pt]
  \item \textbf{v7 (friction-aware):} Trained with per-world weather variation (10\% of worlds assigned a wet surface condition drawn uniformly from SMA, AC, and OGFC road types at varying water film thicknesses).
        The policy receives a 4-element weather context vector $[f_\text{dry}, f_\text{SMA}, f_\text{AC}, f_\text{OGFC}]$ encoding the current surface type; the friction coefficient is embedded into the observation at each step.
        Checkpoint: \texttt{model\_600} ($\sim$314M environment steps).
  \item \textbf{v8 (friction-blind):} Trained exclusively on dry asphalt with no weather variation.
        The weather context observation is held constant at the dry-surface encoding $[0,1,0,0]$ throughout training and evaluation.
        Only the underlying PhysX friction coefficient changes at evaluation time; the policy receives no signal about surface conditions.
        Checkpoint: \texttt{model\_300} ($\sim$157M environment steps).
\end{itemize}

Both models use the same sysid4 vehicle asset (\texttt{comprehensive\_fwd\_v1\_cem\_v4}), the same reward function (v8-fastgoal), the same 256-world random scene pool, and the same PPO hyperparameters.
The only difference is the friction training distribution and whether the weather context observation is live or fixed.

\paragraph{Test configurations.}
Naive evaluation with random friction assignment confounds surface difficulty with scene geometry difficulty: some scenes draw dry asphalt and inflate the success rate regardless of the policy's friction handling.
To isolate the friction variable, we evaluate all conditions on the same 64 held-out test scenes under four \emph{controlled} surface assignments:

\begin{enumerate}[leftmargin=*, itemsep=1pt]
  \item \textbf{Hard rain, original OD.}
        All 64 scenes assigned SMA road surface with 2.0\,mm water film.
        At this depth the Zhao et al.\ friction model predicts full hydrodynamic lift ($\mu_\text{static} = 0.0$, hydroplaning); the simulator applies a minimum floor of $\mu = 10^{-3}$, yielding near-zero traction vs.\ $\mu \approx 1.20$ for dry SMA.
        Dataset-extracted origin--destination pairs (variable agent counts per scene).
        Purpose: stress-test both policies under an extreme low-friction condition.
  \item \textbf{Dry asphalt, original OD.}
        All 64 scenes assigned dry asphalt ($\mu_\text{static} \approx 1.10$).
        Dataset-extracted OD pairs.
        Purpose: verify that friction training does not degrade nominal dry-road performance.
  \item \textbf{Dry asphalt, random OD.}
        All 64 scenes, dry asphalt, with OD pairs re-sampled uniformly at 10--100\,m travel distance (1{,}024 agents, all slots filled).
        Purpose: controlled-agent-count comparison on familiar surface conditions.
  \item \textbf{Hard rain, random OD.}
        All 64 scenes, SMA + 2.0\,mm water film, with random OD at 10--100\,m (1{,}024 agents).
        Purpose: full friction stress test with balanced agent counts.
\end{enumerate}

All evaluations use invincible mode, a 50\,s episode budget, and a 3.0\,m goal threshold.
For conditions using original OD pairs, v7 receives the live SMA/2\,mm weather encoding; v8 receives the fixed dry encoding $[0,1,0,0]$ (its training distribution), so that only the PhysX friction is out-of-distribution for v8.
For dry-asphalt conditions, both models receive the dry encoding, keeping v8 fully in-distribution.

Safety is measured by two additional metrics logged per agent step: \emph{mean TTC} (average time-to-collision with the nearest neighbor over the episode) and \emph{low-TTC fraction} (fraction of control steps where TTC falls below a threshold of 2.0\,s).
Lower friction reduces effective braking distance and is expected to increase close-proximity events even when the goal is reached; these metrics capture safety degradation that SR alone cannot.

\paragraph{Discussion.}
The central finding is a \textbf{null result for friction awareness}: across all four evaluation conditions, v8 (friction-blind) matches or exceeds v7 (friction-aware) in goal-reach rate, and the gap favoring v8 \emph{widens} on wet roads.
On dry asphalt, the two models are nearly tied ($\Delta\text{SR} \leq 0.9\%$), confirming that friction training does not degrade nominal performance.
On hard rain with original OD pairs, v8 leads by 2.6\% (79.2\% vs.\ 76.6\%); on the more demanding random-OD wet condition, the gap grows to 3.6\% (88.2\% vs.\ 84.6\%), accompanied by a substantially lower collision rate for v8 (5.9\% vs.\ 8.3\%).

This reversal relative to our prior hypothesis is informative.
We attribute it primarily to a \emph{credit-assignment cost} introduced by the weather context observation.
In v7, the policy must learn to condition its driving behavior on a 4-element surface-type vector that changes across worlds; this adds a multi-task structure to the policy's learning problem.
With 10\% wet-world exposure and a training budget of $\sim$314M steps, the policy does not fully exploit the conditioning signal---the agent sees wet-surface transitions infrequently enough that the context vector provides marginal value.
Meanwhile, v8 trains exclusively on a single, consistent observation distribution (dry encoding fixed throughout), allowing it to learn a tighter, less variable policy faster.
The result is that v8's simpler inductive bias outperforms v7's richer-but-underexploited observation at these training scales.

A secondary factor is that the SMA 2\,mm condition applies near-zero traction ($\mu \approx 10^{-3}$) at the simulator floor---effectively the most extreme condition the current friction model can produce rather than a moderate wet-road regime.
        Counterintuitively, this extreme condition may still not stress the longitudinal slip limit for 10--100\,m routes at the agent's operating speeds, since the dominant failure mode on such short routes is geometric (sharp turns, goal overshoot) rather than traction-limited braking.

From a platform perspective, the result confirms that SceneFactory's friction module correctly applies out-of-distribution surface conditions at evaluation time: v8 operates under near-zero traction ($\mu \approx 10^{-3}$, full hydroplaning as predicted by the Zhao et al.\ model at 2\,mm water film) while its policy was trained at $\mu \approx 1.20$ (dry SMA).
        Notably, both policies sustain 77--88\% success rates even under this extreme condition, suggesting that the 10--100\,m routes and low operating speeds do not require high longitudinal traction.
        Future work should probe intermediate wet conditions (e.g., 0.3--0.5\,mm water film, $\mu \approx 0.85$--$0.99$, within the Zhao model's calibrated range) or use the simulator's direct $\mu$-override mode to test traction-sensitive regimes where friction-aware training may provide a clearer benefit.

\paragraph{Success modes.}
In the majority of test worlds, agents follow lane centers, decelerate smoothly near goals, and avoid collisions with neighboring vehicles.
The policy learns to yield at merge points when a neighbor vehicle occupies the target lane, demonstrating emergent multi-agent coordination despite using only local observations (24 nearest neighbors within the observation radius).

\paragraph{Failure modes.}
We identify three recurring failure patterns:
\begin{enumerate}[leftmargin=*, itemsep=2pt]
  \item \textbf{Overshoot at sharp turns.}
        In worlds with tight intersections or U-turns, agents carry too much speed into the turn, overshoot the lane boundary, and trigger an off-road crash.
        This failure is absent in kinematic simulators where instantaneous heading changes are possible.
  \item \textbf{Goal approach oscillation.}
        Some agents oscillate near the goal without entering the 3.0\,m acceptance radius.
        The sign-memory brake mechanism (\S\ref{sec:action_space}) mitigates this compared to earlier training runs, but a small fraction of agents still fail to decelerate early enough.
  \item \textbf{Dense-scene congestion.}
        In worlds with all 16 agent slots occupied, vehicles occasionally deadlock when two agents attempt to merge into the same lane segment simultaneously.
        The constant-velocity TTC proxy (\S\ref{sec:sharp_edges}) provides limited lookahead for such scenarios.
\end{enumerate}

\paragraph{Cross-simulator sensor transfer: current limitation and roadmap.}
%
A natural question is whether policies trained in lidar-equipped simulators
(e.g., MetaDrive~\cite{li2022metadrive}, which uses a 240-ray horizontal scanner)
can transfer zero-shot to SceneFactory.
%
At present, such a comparison is not yet physically meaningful.
In the current pipeline, roads are generated from Waymo polyline metadata and consumed
primarily as geometric road-point tensors (centerline/edge samples with type tags) for
policy observations and reward shaping, rather than as lidar-target lane-boundary
collision structures.
%
Although the stage does contain road segment meshes for rendering, they are thin strips
and are not configured as explicit curb/guardrail-like boundary obstacles in our training
setup; in particular, segment collision is typically disabled.
Therefore, a 2-D scan intended to emulate lane-boundary lidar would not reproduce the
same semantics as simulators where rays terminate on physical boundary surfaces.
%
Constructing a synthetic lidar by projecting centerline offsets onto rays
(e.g., $d = \|p_{\mathrm{lane}}\| - w/2$) can yield plausible values, but these values are
not measurements of real collision geometry and should not be treated as physically valid
range returns.

The prerequisite for meaningful cross-simulator lidar transfer is therefore:
\begin{enumerate}[leftmargin=*, itemsep=2pt]
  \item Instantiate lane boundaries as extruded mesh prims with rigid-body collision
        (curbs, guardrails, or thin wall bodies along each lane edge).
  \item Confirm that vehicle bounding boxes already register hits (they do, as Isaac
        Sim assigns rigid-body collision to vehicle USD assets by default).
  \item Replace the current geometric observation group with, or augment it by, a
        vectorized 2-D range scan computed via Isaac~Lab's \texttt{RayCaster}
        sensor~\cite{mittal_orbit_2023}, which batches ray--mesh intersection
        across all agents and worlds in a single Warp kernel call and therefore
        preserves the throughput advantage of the multi-world architecture.
\end{enumerate}
%
Once these geometry prims are in place, a fair head-to-head comparison becomes
possible: train a policy on MetaDrive lidar observations, deploy it in SceneFactory
with an identical 240-ray horizontal scan, and measure zero-shot transfer success
rate, collision rate, and reward.
%
We leave this as a concrete near-term extension; the geometric representation
upgrade is the only blocking dependency, and the sensor infrastructure
(\texttt{RayCaster}, vectorized ray batching) already exists in Isaac~Lab.
